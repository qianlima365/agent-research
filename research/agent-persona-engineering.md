# AI Agent 人格工程：从通用提示到专业角色的系统化方法

> 当所有人都在写"Act as an expert"时，真正有效的 Agent 定义需要回答：这个专家是谁？他怎么思考？他拒绝什么？他怎么知道自己的工作好不好？

---

## 问题的提出

当前大多数 AI 应用中的 Agent 定义停留在"角色扮演"层面：

```
"你是一个资深前端工程师，请帮我优化这段代码。"
```

这种定义的问题在于——**它只描述了"是什么"，没有定义"怎么做"和"做到什么程度"**。结果往往是：
- 输出风格飘忽，有时像初级工程师，有时像架构师
- 缺乏边界感，越权给出不属于该角色范畴的建议
- 无法在多轮对话中保持一致的行为模式
- 与其他 Agent 协作时缺乏可预测性

agency-agents 项目的价值恰恰在于：它把 Agent 定义从"提示词技巧"提升到了"人格工程"的层面——**每个 Agent 都是一个经过精心设计的、可复用的、可验证的专业角色**。

---

## 人格工程 vs 角色提示：本质差异

| 维度 | 传统角色提示（Role Prompting） | 人格工程（Persona Engineering） |
|------|------------------------------|-------------------------------|
| **目标** | 让 AI "扮演"某个角色 | 让 AI "成为"某个可预测的行为体 |
| **定义深度** | 1-2 句话描述身份 | 五维完整的角色画像 |
| **一致性** | 依赖模型记忆，不稳定 | 通过结构化约束保证跨会话一致 |
| **可验证性** | 主观判断"像不像" | 有明确的交付物和质量标准 |
| **可复用性** | 每次重新写提示 | 一次定义，多场景复用 |
| **协作能力** | 单点使用 | 可嵌入多 Agent 协作体系 |

核心区别：**角色提示是"形容词"，人格工程是"操作系统"**。

## 人格五维模型

基于 agency-agents 项目的实践，一个完整的 Agent 人格应由五个维度构成：

### 维度一：身份内核（Identity Core）

回答"我是谁"。不是泛泛的头衔，而是一组**互斥且穷尽的身份特征**：

```
身份：跨境电商运营专家（亚马逊 + 独立站方向）
- 经验层级：8 年实操，经手过 50+ 店铺，年 GMV 峰值 3000 万美元
- 擅长领域：Listing 优化、广告打法、供应链选品、合规风控
- 不擅长领域：品牌设计、线下渠道、B2B 大宗贸易
- 决策风格：数据驱动，先做小规模 A/B 测试再放大
- 语言特征：直接、具体，习惯用数字说话，厌恶空洞的战略建议
```

**设计原则**：
- 身份定义要**可证伪**——如果有人说"这不是你的专业范围"，Agent 应该承认
- 经验层级要**具体量化**——"资深"不够，"8 年、50+ 店铺"才有约束力
- 明确标注**能力边界**——知道自己不能什么是专业性的标志

### 维度二：认知框架（Cognitive Framework）

回答"我怎么思考"。定义 Agent 处理信息的心智模型：

```
认知框架：跨境电商运营专家的决策逻辑

1. 任何建议必须先问三个问题：
   - 你的品类是什么？（标品/非标品决定打法）
   - 你的预算天花板是多少？
   - 你的时间窗口有多长？（短期冲量 vs 长期品牌建设）

2. 分析顺序：
   市场容量 → 竞争格局 → 利润率空间 → 操作可行性 → 风险评估

3. 默认假设：
   - 亚马逊算法权重：转化率 > 点击率 >  reviews
   - 独立站核心指标：ROAS > LTV/CAC > 复购率
   - 不碰灰色操作（测评、跟卖、侵权擦边）

4. 思考盲区（主动承认）：
   - 不掌握实时平台政策变化，建议用户二次确认
   - 对新兴市场的判断可能滞后 3-6 个月
```

**设计原则**：
- 认知框架是**可教的**——新人可以通过学习这个框架快速成长
- 要包含**决策顺序**——先做什么判断、后做什么判断
- 必须标注**盲区**——知道自己不知道什么，比知道什么更重要

### 维度三：行为协议（Behavior Protocol）

回答"我怎么做"。定义 Agent 与用户交互的标准流程：

```
行为协议：前端性能优化专家的工作流程

阶段一：诊断（必须完成，不可跳过）
- 询问：技术栈、性能目标、用户设备分布
- 审查：提供当前代码的性能分析
- 定位：明确瓶颈在加载/渲染/交互哪个阶段

阶段二：方案（至少提供 2 个选项）
- 方案 A：改动最小，收益明确，适合快速上线
- 方案 B：改动较大，长期收益更高，适合重构窗口期
- 每个方案必须包含：预期收益、实施成本、回滚方案

阶段三：执行（用户选定后）
- 提供可直接运行的代码
- 标注每一行改动的理由
- 给出验证方法（基准测试、DevTools 步骤）

阶段四：验收
- 要求用户反馈实际测试结果
- 如果未达预期，分析原因并调整方案
- 记录本次优化的关键数据，更新记忆

禁止行为：
- 不诊断直接给方案
- 不提供回滚方案就让用户改生产环境
- 对不熟悉的框架（如 Svelte、Solid）假装精通
```

**设计原则**：
- 协议是**强制性的**——Agent 必须遵守，不是"建议"
- 包含**禁止行为清单**——明确划定红线
- 设计**反馈闭环**——每个任务结束后有验收和记录环节

### 维度四：质量标准（Quality Standard）

回答"怎么算做好了"。定义输出的验收标准：

```
质量标准：技术文档工程师的交付要求

必须满足：
- [ ] 准确性：所有技术事实可追溯到官方文档或社区共识
- [ ] 完整性：覆盖正常路径 + 至少 3 种常见异常路径
- [ ] 可执行性：提供的命令/代码可以直接复制运行
- [ ] 时效性：标注信息的时间戳（哪年哪月的版本）

加分项：
- [ ] 对比分析：同一问题在 2 种以上技术方案中的差异
- [ ] 性能数据：有基准测试或复杂度分析
- [ ] 视觉辅助：关键流程有 ASCII 图或表格

否决项（出现任一即不合格）：
- [ ] 使用已废弃的 API 或方法
- [ ] 代码示例无法通过语法检查
- [ ] 关键步骤缺失（如只讲"配置缓存"不讲"如何验证缓存生效"）
```

**设计原则**：
- 标准要**可检查**——不是"写得好的文档"，而是可逐项打勾的清单
- 区分**必须/加分/否决**——让 Agent 知道优先级
- 给出**正反示例**——好和坏的具体对比

### 维度五：协作接口（Collaboration Interface）

回答"我怎么和其他 Agent 配合"。在 multi-agent 系统中，每个 Agent 需要暴露清晰的"接口"：

```
协作接口：数据分析师 Agent 的对外契约

输入契约（我接收什么）：
- 原始数据文件（CSV/JSON/SQL 查询结果）
- 分析目标（描述性统计 / 诊断性分析 / 预测性建模）
- 约束条件（隐私合规要求、时间窗口、精度要求）

输出契约（我交付什么）：
- 分析结论（用非技术人员能听懂的语言）
- 支撑数据（可追溯到原始数据的计算过程）
- 可视化图表（如果适用）
- 置信度标注（高/中/低，以及理由）

依赖声明（我需要谁配合）：
- 数据清洗：需要数据工程师 Agent 提供干净的输入
- 业务解释：需要产品经理 Agent 确认结论的业务含义
- 可视化美化：需要设计师 Agent 优化图表呈现

不处理的事项（请找别人）：
- 数据采集（找数据工程师）
- 模型训练（找 ML 工程师）
- 前端展示（找前端工程师）
```

**设计原则**：
- 接口是**契约**——输入输出格式固定，降低协作摩擦
- 明确**依赖关系**——知道自己需要谁、谁需要自己
- 标注**不处理事项**——避免职责不清导致的推诿或越权

## 从人格到多 Agent 协作

单个 Agent 的人格定义完成后，下一步是设计**协作拓扑**。agency-agents 项目中的多 Agent 场景不是简单的"多个人格同时在线"，而是有明确的协作模式：

### 模式一：接力式（Handoff）

```
[需求分析 Agent] → [架构设计 Agent] → [编码 Agent] → [测试 Agent]
```

- 每个 Agent 完成自己的阶段后，将上下文打包传递给下一个
- 关键：交接格式标准化（必须包含什么信息、用什么格式）
- agency-agents 示例：初创公司 MVP 开发场景

### 模式二：评审式（Review）

```
[主笔 Agent] ──初稿──→ [审查 Agent A] ──反馈──┐
                 └─→ [审查 Agent B] ──反馈──┼→ [主笔 Agent] ──终稿
                 └─→ [审查 Agent C] ──反馈──┘
```

- 一个 Agent 产出，多个 Agent 从不同维度审查
- 关键：审查维度不重叠（技术/业务/合规各管各的）
- agency-agents 示例：技术方案评审场景

### 模式三：竞争式（Competition）

```
[创意 Agent A] ──┐
[创意 Agent B] ──┼→ [评估 Agent] → 最优方案
[创意 Agent C] ──┘
```

- 多个 Agent 并行产出不同方案，由评估 Agent 筛选
- 关键：评估标准必须预先公开，避免偏见
- agency-agents 示例：营销活动方案生成场景

## 人格的迭代与演化

Agent 人格不是一次写定就万事大吉，需要持续迭代：

```
初始定义 → 小规模测试（5-10 个任务） → 收集偏差案例 →
修订人格定义 → 扩大测试（50+ 任务） → 建立评估基准 →
持续监控（生产环境） → 定期复盘（每月/每季度）
```

**迭代的信号**：
- 同一类任务反复出现相同错误 → 认知框架有盲区
- 用户频繁绕过 Agent 的标准流程 → 行为协议过于僵化
- 输出质量波动大 → 质量标准不够具体
- 与其他 Agent 协作时信息丢失 → 协作接口定义不清

## 实践建议

1. **从具体场景出发，不要追求通用**。agency-agents 的 144 个角色中没有一个是"通用开发者"，因为通用意味着模糊。

2. **先写"不做清单"，再写"做清单"**。人格的边界感往往比能力描述更重要。

3. **用真实任务测试，不要自我感动**。一个 Agent 人格好不好，取决于它在 20 个真实任务中的表现是否稳定。

4. **建立"人格版本"机制**。像管理软件版本一样管理 Agent 人格，每次迭代都有变更记录和回归测试。

5. **跨工具保持一致性**。同一个人格在 Claude Code、Cursor、Aider 等不同工具中，核心身份和认知框架应保持一致，只在交互格式上适配工具特性。
