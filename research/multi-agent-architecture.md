# 多智能体基础架构研究

> Multi-Agent System (MAS) 不是多个单智能体的简单堆叠，而是一套关于分工、协作、冲突解决与涌现行为的工程体系。

---

## 核心问题域

设计多智能体系统时，需要回答四个根本问题：

| 问题 | 决策维度 |
|------|---------|
| **Who** | 需要哪些类型的 Agent？各自的角色与能力边界？ |
| **What** | Agent 之间传递什么信息？状态、指令、还是中间产物？ |
| **How** | Agent 如何协调？中心化调度、去中心化协商，还是混合模式？ |
| **When** | 何时触发协作？串行流水线、并行竞争，还是事件驱动？ |

这四个问题的答案组合，决定了系统的整体架构形态。

## 经典架构模式

### 1. 层级式（Hierarchical）

```
        ┌─────────────┐
        │   规划者    │  ← 分解任务、分配子目标
        └──────┬──────┘
       ┌──────┴──────┐
    ┌──┴──┐      ┌──┴──┐
    │执行A│      │执行B│  ← 各自独立完成子任务
    └─────┘      └─────┘
```

- **特点**：一个中央规划者（Orchestrator）将复杂任务分解为子任务，分发给下层执行 Agent
- **优势**：结构清晰、责任明确、适合确定性强的流程
- **劣势**：单点瓶颈、规划者负载重、容错性差
- **代表项目**：LangChain 的 RunnableSequence、AutoGen 的 GroupChatManager

### 2. 对等网络（Peer-to-Peer）

```
    ┌───┐ ←──→ ┌───┐
    │ A │      │ B │
    └───┘ ←──→ └───┘
      ↑   ↘↗   ↑
      └────┬───┘
           ↓
         ┌───┐
         │ C │
         └───┘
```

- **特点**：Agent 之间直接通信，无中心节点，通过协商达成共识
- **优势**：可扩展性强、单点故障影响小、灵活性高
- **劣势**：协调开销大、可能产生冲突循环、调试困难
- **代表项目**：CAMEL 的 Role-Playing 框架、MetaGPT 的 SOP 协作

### 3. 市场/拍卖式（Market-based）

```
    Agent A ──出价──┐
    Agent B ──出价──┼→ 拍卖市场 ──→ 任务分配
    Agent C ──出价──┘
```

- **特点**：引入"虚拟经济"机制，Agent 通过竞标获取任务
- **优势**：负载均衡自然形成、资源利用率高
- **劣势**：拍卖机制本身有开销、不适合实时性要求高的场景
- **应用场景**：动态任务分配、资源调度（如 Kubernetes + AI Agent）

### 4. 黑板式（Blackboard）

```
    ┌─────────────────────────┐
    │      共享黑板（全局状态）   │
    │  问题描述 | 中间假设 | 部分解  │
    └─────────────────────────┘
      ↑      ↑      ↑      ↑
   专家A  专家B  专家C  专家D
```

- **特点**：所有 Agent 向一个共享的"黑板"读写信息，无直接通信
- **优势**：解耦程度高、新 Agent 易于接入、状态可追溯
- **劣势**：黑板可能成为瓶颈、并发写入需要锁机制
- **现代变体**：基于向量数据库的长期记忆共享、Redis Pub/Sub

### 5. 流水线式（Pipeline）

```
    输入 → [Agent A] → [Agent B] → [Agent C] → 输出
           提取       分析       生成
```

- **特点**：Agent 按固定顺序串联，前一级的输出是后一级的输入
- **优势**：数据流清晰、易于调试和监控
- **劣势**：灵活性差、任一节点故障导致整条链路中断
- **代表项目**：LangChain LCEL、Hugging Face Transformers Pipeline

## 通信机制对比

| 机制 | 描述 | 适用场景 |
|------|------|---------|
| **消息传递** | Agent 直接发送/接收结构化消息 | 实时协作、低延迟 |
| **共享内存** | 通过中央存储读写状态 | 需要强一致性、状态复用 |
| **事件驱动** | 发布-订阅模式，Agent 响应事件 | 解耦、异步处理 |
| **RPC 调用** | 同步请求-响应 | 需要即时反馈的决策 |

实践中往往是混合使用：比如用 **事件驱动** 触发协作，用 **共享内存** 持久化中间状态，用 **消息传递** 进行细粒度协调。

## 关键设计权衡

### 中心化 vs 去中心化

| 维度 | 中心化 | 去中心化 |
|------|--------|---------|
| 决策速度 | 快（单点决策） | 慢（需要协商） |
| 可扩展性 | 受限于中心节点 | 理论上无限 |
| 容错性 | 中心节点故障即瘫痪 | 部分 Agent 失效可继续 |
| 调试难度 | 低（流程确定） | 高（涌现行为不可预测） |
| 适用场景 | 企业流程、确定性任务 | 创意生成、探索性任务 |

**折中方案**："中心化规划 + 去中心化执行"。中央节点负责任务分解和调度，执行 Agent 之间自主协调。

### 串行 vs 并行

- **串行**：数据依赖强，前一级的输出是后一级的必要输入
- **并行**：子任务相互独立，可同时进行，最后汇总结果
- **混合**：先并行探索多个方案，再串行评估筛选最优解

AutoGen 的 GroupChat 是一个典型混合模式：多个 Agent 并行发言，Manager 串行决定下一步由谁发言。

## 状态管理

多智能体系统的状态可以分为三层：

```
┌─────────────────────────────────────┐
│  Layer 3: 长期记忆（向量数据库）      │  ← 跨会话持久化知识
│  Pinecone / Milvus / Chroma / Redis  │
├─────────────────────────────────────┤
│  Layer 2: 会话状态（上下文窗口）       │  ← 当前对话历史
│  各 Agent 独立的 system prompt + chat │
├─────────────────────────────────────┤
│  Layer 1: 任务状态（执行跟踪）         │  ← 任务进度、中间产物
│  共享的待办列表、工作流状态机          │
└─────────────────────────────────────┘
```

**关键决策**：哪些状态共享？哪些私有？
- 共享过多 → 信息过载、Agent 决策质量下降
- 共享过少 → 协作断裂、重复劳动

实践中通常采用"按需共享"：Agent 只读取与其当前任务相关的状态片段，而非全局状态。

## 冲突解决

多 Agent 协作必然产生冲突，常见类型：

| 冲突类型 | 示例 | 解决策略 |
|---------|------|---------|
| **资源竞争** | 两个 Agent 同时修改同一份文档 | 锁机制、乐观并发控制 |
| **目标冲突** | 优化成本的 Agent vs 优化质量的 Agent | 多目标优化、Pareto 前沿 |
| **信念冲突** | 两个 Agent 基于不同信息得出矛盾结论 | 置信度投票、证据聚合 |
| **行动冲突** | Agent A 删除文件，Agent B 同时编辑该文件 | 事务回滚、操作队列 |

**MetaGPT 的解决方案**：通过严格的 SOP（标准作业程序）预先定义协作流程，从根本上避免大部分冲突。

## 可观测性

多 Agent 系统的调试比单 Agent 困难一个数量级，需要专门的可观测性基础设施：

- **执行追踪**：每个 Agent 的输入、输出、工具调用、耗时
- **状态快照**：关键时间点的全局状态记录
- **通信图谱**：Agent 之间的消息流向可视化
- **决策回放**：完整重现一次协作过程

**代表工具**：LangSmith、Langfuse、OpenTelemetry + 自定义 exporter

---

## 前沿趋势

1. **Agent 即服务（AaaS）**：将 Agent 封装为可复用的微服务，通过 API 编排
2. **自组织多智能体**：Agent 动态组建团队、分配角色，无需预设架构
3. **人机混合团队**：人类与 Agent 平等参与协作流程，而非单向指令
4. **跨模态协作**：文本 Agent、图像 Agent、代码 Agent 协同完成复杂创意任务
