# 权限模型与安全设计

## 权限矩阵

| 操作类型 | 默认权限 | 需要确认 |
|---------|---------|---------|
| 读取文件 | ✅ 允许 | 否 |
| 写入文件 | ⚠️ 需授权 | 是 |
| 执行命令 | ⚠️ 需授权 | 是 |
| 删除文件 | ❌ 禁止 | 必须人类确认 |
| 网络请求 | ⚠️ 需授权 | 是 |

---

## 设计理由

在代码开发场景中，一个失控的 Agent 可能：
- 误删生产环境文件
- 引入安全漏洞（如 SQL 注入）
- 执行恶意命令（如 `rm -rf /`）

Orchestrator 作为"内核"，严格控制每个子进程的权限。子 Agent 默认**只读**，只有 Orchestrator 能决定是否授予写入权限。

---

## 权限升级流程

```
Agent 请求写入文件
    ↓
Orchestrator 评估风险
    ↓
低风险（测试文件）→ 自动授权
中风险（源代码）→ 提示人类确认
高风险（配置文件）→ 拒绝，要求人工操作
```

---

## 与 OpenClaw 的对比

| 维度 | Claude Code | OpenClaw |
|------|------------|----------|
| **权限控制** | Orchestrator 集中管控 | 契约声明 + 运行时检查 |
| **默认状态** | 只读 | 取决于配置 |
| **危险操作** | 必须人类确认 | 依赖配置约束 |
| **可审计性** | 操作日志完整可追溯 | 依赖外部系统 |
